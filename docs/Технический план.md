# **Технический план**

[[ГДД Мастер на день|Главный ГДД]]


## **Статус**

По этому плану реализована играбельная версия игры (папка `game/`): вся кампания, пять локаций, все механики ГДД, сохранение, тесты. Отличия от плана: модели сделаны процедурно в коде без Blender; дополнительно сделаны адаптация под телефоны и процедурная музыка. Этапы 6–8 (плейтест с игроками, полировка, публикация) остаются следующими шагами.

## **Стек**

| Слой | Технология | Зачем |
| :---- | :---- | :---- |
| Язык | TypeScript (strict) | правила ГДД — это много формул и состояний; типы ловят ошибки до запуска |
| Сборка | Vite | быстрый dev-сервер, статическая сборка для itch.io |
| 3D | Three.js | одна комната, вращение камеры, выбор предметов лучом, контур при наведении |
| Интерфейс | Vue 3 поверх canvas | 10 экранов с формами и состоянием удобнее делать в DOM, чем рисовать в 3D; Vue был выбран ещё в концепте |
| Миниигры | Canvas 2D | простая графика, точный контроль ввода и таймера |
| Звук | Web Audio API | без зависимостей, общая громкость из настроек |
| Тесты логики | Vitest | каждая формула реестра — отдельный тест |
| Тесты в браузере | Playwright | сквозные сценарии и скриншоты для проверки визуала |
| Публикация | itch.io (HTML5) | ZIP со статикой |

## **Архитектура**

Главный принцип: **игровая логика отделена от отображения.** Ядро — чистый TypeScript без DOM и Three.js. Его можно протестировать и прогнать в симуляции тысячи кампаний, а 3D и интерфейс только показывают состояние и отправляют действия игрока.

```
src/
  core/            чистая логика, без DOM
    rng.ts           сидируемый генератор случайных чисел
    params.ts        все числа из «Реестра параметров игры» в одном месте
    types.ts         кампания, предложение, клиент, заказ, предметы комнаты
    content.ts       устройства, неисправности, предметы, реплики, имена
    rules.ts         формулы: предел согласия, обнаружение наценки, шанс инспектора, репутация
    campaign.ts      этапы заказа, локации, квоты, переезды, победа и поражение
    save.ts          сохранение и настройки
  scene/           Three.js: инструменты моделирования, предметы и устройства, комнаты, клиент, камера и выбор предметов
  minigames/       четыре миниигры на Canvas 2D
  ui/              экраны и компоненты Vue (бумага, штамп, рулетка, чек)
  game/            состояние игры: связь ядра с интерфейсом и автосохранение
  audio/           процедурные звуки и музыка
tests/
  core/            Vitest: формулы, граничные случаи, повторная загрузка
  sim/             симуляция кампаний на коде игры (тот же расчёт, что в tools/balance_sim.py)
  e2e/             Playwright: полные сценарии, мобильная вёрстка, скриншоты
```

### Этапы заказа (машина состояний)

`ВЫБОР → ОСМОТР → ДИАЛОГ → ДИАГНОСТИКА → ЦЕНА → (ТОРГ) → РЕМОНТ → ОПЛАТА → (ПРОТОКОЛ) → ИТОГ`

Боковые исходы: `УХОД ПОСЛЕ ТОРГА`, `ЖАЛОБА СКАНДАЛЬНОГО`. Любой этап записывается в сохранение до показа результата.

### Детерминизм и сохранение

ГДД требует, чтобы загрузка не меняла исходы. Поэтому:
1. Каждый случайный бросок выполняется один раз и **записывается в состояние до показа** (обнаружение наценки, тип требования, согласие при хорошем настроении, роль, предметы).
2. Денежные и репутационные последствия применяются через события с флагом «обработано» — повторная загрузка их не дублирует.
3. Таймер осмотра хранит момент окончания (абсолютное время), а не остаток.
4. Сохранение — `localStorage`, JSON с номером версии схемы; при изменении структуры пишется миграция.

### Контур при наведении

Одинаковый тонкий контур для всех интерактивных предметов. Реализация: `OutlinePass` из примеров Three.js или «inverted hull» (второй меш с вывернутыми нормалями). Выбор — по замеру производительности на этапе 2.

## **Этапы работы**

Оценки — в рабочих днях для одного разработчика. Каждый этап заканчивается проверяемой контрольной точкой.

| № | Этап | Содержание | Контрольная точка | Дней |
| :---- | :---- | :---- | :---- | :---- |
| 0 | Подготовка | проект Vite + TS + Vue + Three, линтер, Vitest, Playwright, структура папок, git | пустая сцена и экран меню открываются, тесты запускаются | 1 |
| 1 | Ядро логики | все правила ГДД в `core/`, параметры из реестра, тесты на каждую формулу, симуляция на TS | кампания проходится целиком в тестах; симуляция совпадает с Python-версией (±2 %) | 4 |
| 2 | Серая версия | комната из блоков, камера с ограничениями, выбор предметов, таймер, все экраны в черновом виде, 4 миниигры в черновом виде | **всю кампанию можно пройти в браузере** от меню до финала | 5 |
| 3 | Сохранение | сохранение на каждом этапе, загрузка, граничные случаи ГДД | закрытие вкладки на любом этапе не меняет исход и не дублирует деньги | 2 |
| 4 | Вертикальный срез: общежитие | арт-дирекшн на одной локации: 2 комнаты, 3 устройства, предметы, клиент, интерфейс «бумаги мастера», свет, звук | скриншоты общежития проходят шкалу визуала (≥ 2 из 3 по каждой категории) | 6 |
| 5 | Контент | остальные 4 локации: 8 комнат, 12 устройств, предметы, окна, фоны звука | все 5 локаций в финальном стиле | 7 |
| 6 | Плейтест и баланс | 3–5 игроков из ЦА, журнал игры (экспорт JSON), настройка квот и шансов | цели плейтеста достигнуты (см. ниже) | 3 |
| 7 | Полировка и QA | анимации, переходы, доступность с клавиатуры, производительность, исправление ошибок | 60 кадров/с на целевом устройстве, сквозные тесты зелёные | 3 |
| 8 | Релиз | сборка, страница на itch.io, пояснительная записка, сценарий защиты | игра опубликована, записка готова | 2 |
| | **Итого** | | | **≈ 33** |

Если срок короче — первым режется этап 5: вместо 5 локаций в финальном стиле делаются 3, остальные остаются в упрощённом стиле с тем же контентом.

## **Баланс под целевую аудиторию**

ЦА по концепту — 14–17 лет, любители казуальных игр. Цели плейтеста:

| Метрика | Цель |
| :---- | :---- |
| Победа в первой кампании | 30–40 % игроков |
| Победа во второй кампании | 60 % и выше — игрок учится читать клиентов |
| Длительность кампании | 40–60 минут (15 заказов по 2–3 минуты) |
| Поражения по причинам | ни одна причина не больше 50 %; поражение должно быть понятным |
| Ремонт с первой попытки | 85–90 % |
| «Поражение было нечестным» (опрос) | меньше 20 % игроков |

Регуляторы, если цели не достигнуты: квоты (±5 %), шанс заметить наценку (K), шанс инспектора, сложность миниигр. Все числа живут в `core/params.ts`, поэтому меняются без правки логики.

## **Риски**

| Риск | Чем опасен | Что делаем |
| :---- | :---- | :---- |
| Объём 3D-контента | 10 комнат и около 50 моделей — самая долгая часть | процедурные модели в коде, общий атлас, вертикальный срез до массового контента |
| Качество клиента | плохой персонаж портит весь кадр | лицо как текстура, минимальная анимация, сначала проверить на срезе |
| Расхождение кода и ГДД | ошибки в формулах ломают баланс | тест на каждую строку реестра; симуляция на реальном ядре |
| Производительность | слабые ноутбуки | бюджет треугольников и вызовов отрисовки, запечённое затенение |
| Сроки | курсовая с дедлайном | контрольные точки; этап 5 можно сократить |
